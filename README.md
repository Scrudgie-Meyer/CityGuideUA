# CityGuide UA 2

Вебдовідник міст України з серверною базою SQLite, Wikidata та SPARQL. Початкові 12 міст є стартовим набором: каталог може поповнюватися новими QID. Браузер показує дані та зберігає приватне обране, а сервер зберігає спільний каталог, джерела й RDF-граф та виконує семантичні запити.

Усі файли цього релізу знаходяться в `ForGitProject/CityGuideUA`.

## Запуск

Потрібен Node.js 24. Відкрийте цю папку у VS Code, далі Terminal → New Terminal:

```powershell
npm ci
npm start
```

Відкрийте **http://localhost:3000**. Перший запуск створить `data/cityguide.sqlite` і наповнить його з початкового JSON. Наступні запуски використовують збережену базу, не скидаючи її до 12 міст. Ctrl+C завершує сервер.

SQLite вбудований у Node.js, тому встановлювати окремий сервер бази не потрібно. ESLint і Prettier є залежностями тільки для розробки. Серверні обчислення, SQL і SPARQL тепер працюють у Node.js; локальний пошук та відображення карток працюють у браузері.

`.env.example` є прикладом змінних. Автоматично файл `.env` не читається. Для іншого шляху бази в PowerShell:

```powershell
$env:DATABASE_PATH = 'C:\Data\CityGuide\cityguide.sqlite'
npm start
```

## Розширення графа та резервування

Додати або оновити міста за їхніми Wikidata QID:

```powershell
npm run import -- Q1899 Q36036
```

Цей приклад оновить Київ і Львів. Вкажіть інші QID українських міст, щоб додати нові записи. Програма не перевіряє повну ієрархію P31: адміністратор має обирати саме міста, а імпортер перевіряє QID, країну, координати та числові значення. Усі записи з інших імпортів зберігаються. Імпорт перевіряє повний пакет до транзакційного запису. На Railway команду потрібно запускати всередині того самого сервісу, де змонтовано його Volume; локальна команда змінює тільки локальну базу.

Кнопка оновлення на сайті оновлює всі QID, які вже є в серверній БД, а не тільки стартові 12. Оновлення доступне раз на хвилину. Якщо Wikidata недоступна або один запис не проходить перевірку, попередній каталог і граф залишаються в БД.

Послідовне резервування:

```powershell
npm run backup -- data/backup-2026-11-06.sqlite
```

Файл призначення не має існувати. Backup створюється через SQLite VACUUM INTO і включає завершені WAL-транзакції. Збережіть резервну копію окремо від робочого диска. Для відновлення зупиніть сервер і задайте DATABASE_PATH на перевірений файл резервної копії. Не замінюйте вручну файли відкритої бази.

## GitHub через VS Code

Ця папка розташована всередині іншого Git-репозиторію SemanticWeb. Відкриття її у VS Code саме по собі не створює окремого репозиторію. Якщо потрібен незалежний репозиторій тільки сайту, його корінь має бути саме ця папка: перед Commit перевірте, що Source Control не включає лабораторні роботи з батьківського каталогу. Ініціалізацію окремого репозиторію та його публікацію виконуйте свідомо через VS Code/Git. Автоматичної публікації у ваш особистий GitHub не виконано.

Після початкового завантаження гілки main:

1. На GitHub відкрийте Actions і дочекайтесь успішного `CI / quality`.
2. Settings → Branches → Add classic branch protection rule, гілка `main`, або створіть еквівалентний активний Ruleset.
3. Увімкніть **Require a pull request before merging**.
4. Увімкніть **Require status checks to pass before merging**, додайте перевірку `quality` із workflow CI.
5. Увімкніть **Require branches to be up to date before merging** та **Do not allow bypassing the above settings**. У Ruleset залиште bypass list порожнім.
6. Не дозволяйте force push та видалення main. Для індивідуальної роботи не вимагайте схвалення іншою людиною, якщо її немає в команді.

Workflow не вмикає захист гілки автоматично. GitHub перевіряє зміни перед злиттям PR, а не перед локальним commit. Для приватного репозиторію доступність правил залежить від тарифу GitHub.

Подальша робота: оновіть main → створіть feature-гілку у VS Code → внесіть зміни → Commit/Push → Pull Request у main → дочекайтесь quality → Merge. Після merge CI перевірить main ще раз, і Railway з Wait for CI дочекається результату.

## Railway та постійна база

1. New Project → Deploy from GitHub repo, оберіть свій репозиторій.
2. Deployment branch: `main`. Root Directory: корінь цього проєкту. Якщо сайт у репозиторії SemanticWeb, вкажіть фактичний шлях до CityGuideUA, а workflow має лежати в `.github/workflows` кореня GitHub-репозиторію. Наявний workflow розрахований на окремий репозиторій цього проєкту.
3. Railway використовує Dockerfile. Команда запуску — `node server.mjs`, healthcheck — `/healthz`.
4. **Створіть Volume для сервісу сайту і змонтуйте його в `/app/data`.** Без Volume сервер у Railway відмовиться запускатися, щоб випадково не втратити БД під час наступного deploy.
5. Додайте змінну сервісу **`RAILWAY_RUN_UID=0`**. За документацією Railway Volume належить root, а наш Docker image за замовчуванням використовує користувача node. Для локального запуску ця змінна не потрібна.
6. DATABASE_PATH можна не задавати: застосунок використає RAILWAY_VOLUME_MOUNT_PATH і файл cityguide.sqlite всередині диска. Якщо задаєте явно, використайте `/app/data/cityguide.sqlite`.
7. Увімкніть **Wait for CI**, потім Networking → Generate Domain.
8. Залиште **одну репліку сервісу**. SQLite-файл не є спільною БД для кількох незалежних серверів. Для такого масштабування слід замінити репозиторій на PostgreSQL або спеціалізоване RDF-сховище.

Переконайтесь, що новий deploy читає наявну БД: перевірте розмір каталогу після перезапуску сервісу. Railway та Volume використовують ресурси відповідно до вашого тарифу. Налаштування Volume, GitHub integration і branch protection у ваших облікових записах не створено автоматично.

## Стиль і перевірки

```powershell
npm run format
npm run check
npm test
npm run test:coverage
```

ESLint перевіряє правила коду, Prettier — єдине форматування. У GitHub CI виконуються npm ci, ці перевірки, тести з покриттям, збірка Docker і перевірка запущеного контейнера. Стилістичні помилки блокують quality так само, як помилки тестів.

Тести використовують справжні Wikidata-fixtures та окремі SQLite-бази. Перевірено збереження після повторного відкриття, розширення до 13 записів, атомарний rollback, backup, мережеві помилки, серверний SPARQL, API та доступність статичних файлів. Синтетичний 13-й запис існує тільки в тимчасовому тесті, не в початковому каталозі. Це часткове покриття: DOM перевіряється окремо, а відсотки Node coverage стосуються завантажених тестами модулів. Docker локально не встановлений; його збірку перевірить GitHub після публікації.
